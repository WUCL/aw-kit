## 與計畫預期的落差

1. **呼叫點數量：計畫預測 14 個檔案，實際是 16 個。**
   原遷移計畫基於遷移前的 grep survey，預估要改 App.jsx + 13 個呼叫點。但程式碼品質審查（而非原始 survey）另外抓到 2 個被漏掉的檔案：`src/lib/undoDelete.js` 與 `src/lib/orderWrite.js`。這兩個檔案因為本身就位於 `src/lib/` 目錄內，是用**相對路徑** `'./toast'` 匯入 toast，而不是其他 13 個檔案使用的 `'../lib/toast'` 樣式。原始 survey 的 grep pattern 顯然沒有涵蓋到這種「相對深度不同」的匯入變體，或者這兩個檔案根本不在其搜尋範圍內。

2. **這個遺漏在實務上會造成什麼問題：** 因為 `App.jsx` 已經改成掛載 `aw-notify-kit` 的 `ToastHost`（不再掛載專案舊有的 `ToastHost`），而 `aw-notify-kit` 的 `toast` 是與專案自己的 `src/lib/toast.js` 完全獨立的 module-singleton emitter，這兩個檔案若沒被抓到並修正，它們的 `toast.success()`／`toast.error()` 呼叫會繼續寫入一個沒有任何訂閱者的「死」emitter——導致「可復原刪除」流程（`undoDelete.js`，被 OrderList、VendorList、CustomerDetail、ExpenseForm、ExpenseQuickView 使用）與訂單建立/指派/刪除流程（`orderWrite.js`）的所有 toast 提示全部靜默失效。不會拋出任何錯誤，唯一症狀是「UI 提示消失」——這正是那種光靠不夠徹底的 grep 或不做點擊測試就很難抓到的 bug。

3. **修正這 2 個檔案連帶需要更新 2 個測試檔案：** `tests/undoDelete.test.js`、`tests/orderWrite.test.js` 原本的 `vi.mock('../src/lib/toast', ...)` 在 import path 修正後已經對不上實際路徑，mock target 必須改成 `vi.mock('aw-notify-kit', ...)`。若沒有同步修正，會有 10 個測試從「真正的斷言」退化成「假陽性通過」（mock 不再攔截任何呼叫，程式碼內的 `toast.success`/`toast.error` 呼叫變成靜默無操作、剛好不會拋錯，測試因此照樣綠燈）。

4. **修正後，全部 16 個檔案（非原計畫的 14 個）都與 `aw-notify-kit` 的 API 完全吻合**，沒有其他 API 不符或 prop 形狀差異。原本被標記需留意的 `Button size="sm"` 疑慮最終證實是多慮——那個用法只存在於已被刪除的 `ConfirmDialogHost.jsx` 內部，隨檔案刪除一併消失。

5. **計畫原本提醒的 CSS import 風險並未發生。** 計畫曾提醒 `import 'aw-notify-kit/dist/style.css'` 有可能在 Vitest 中出現「Unknown file extension .css」錯誤（常見於 Jest 環境）。實際上本專案用的是 Vite + Vitest，CSS import 預設就透過 Vite transform pipeline 處理，且測試套件中沒有任何測試會 import 到 `App.jsx`，因此這個 import 在這次遷移中根本沒被測試套件實際執行到，風險並未被驗證到也未發生。

6. **人工與瀏覽器驗證均正常，無落差。** 使用者本機測試 + Chrome DevTools MCP 瀏覽器檢查：app 載入零 console 錯誤/警告；確認 DOM 中存在 `aria-live="polite"` 的 toast container（套件的 `ToastHost` 正確掛載）；套件的 `ConfirmDialogHost` 透過真實 UI 操作被觸發驗證（嘗試刪除一個仍有採購紀錄關聯的廠商，正確觸發「無法刪除廠商」提示型 confirm gate）——渲染正確（白色圓角面板、暗化背景、紫色主按鈕符合品牌 `--fbk-accent` 主題值），且乾淨關閉、無 console 錯誤。

## 建議 aw-notify-kit 改善的項目（若有）

1. **README 或新增一份「從既有 in-house 實作遷移」指南，明確提醒兩件事：**
   - (1) 搜尋舊模組時，應以「內容特徵／使用模式」（例如搜尋 `toast.success(`、`toast.error(`、`from ['"].*toast['"]` 的 regex，涵蓋任意相對深度）而非單一寫死深度的 import 字串（如只搜 `'../lib/toast'`）來定位所有呼叫點，避免像本次一樣漏掉 `'./toast'` 這種同層相對匯入。
   - (2) 提醒不要只查生產碼——**既有測試中的 `vi.mock(...)`／`jest.mock(...)` 也必須同步更新 mock target**，否則 mock 會悄悄停止攔截，測試從真斷言退化成假陽性通過，且不會有任何錯誤訊息提示。
2. 若日後要提供官方遷移腳本／checklist，可以把上述兩點直接列成两條可執行的檢查項（例如附上建議的 grep regex 範例），降低下一個消費專案重複踩坑的機率。
3. 其餘部分（安裝流程、build/lint 相容性、CSS import、`ToastHost`／`ConfirmDialogHost` 實際渲染與主題色套用）沒有發現需要改善之處。
